# pearljs gaps found while building the dashboard

Things the dashboard needed from pearljs and had to work around. None of them is patched here.

1. Certificate version 4 (FP8) is not parsed. Pearl's testnet moved to V4 certificates at height 67370 on 2026-11-17 (branch `fp8-scheme`), so `parseBlock`, and with it `followChain`, stops there on testnet. Mainnet and testnet2 are still on V3, so the dashboard is unaffected on mainnet until the FP8 fork reaches it. The dashboard stores `cert_version` and `cert_kind` as reported and will show V4 once pearljs parses it; `isMoECertificate` will need a rule for V4 too.
2. No CA-trusting `fetch` outside the test kit. pearld serves RPC over TLS with a self-signed `rpc.cert`. pearljs's docs show the way through undici (`Agent` with the certificate, passed to `fetch` and `WebSocket`), and the dashboard now does that in `src/node.ts`, at the cost of its own `undici` dependency; an earlier version hand-rolled a `node:https` fetch. A `ca` option on `PearldClient` and `PearlWsClient` would let an app trust `rpc.cert` without knowing about undici.
3. `spendableUtxos` (and so `payFromAccount`) defaults `coinbaseMaturity` to `COINBASE_MATURITY` (100), not to `network.coinbaseMaturity`. On a `customNetwork` with a short maturity, a coinbase output with enough confirmations is still refused unless `coinbaseMaturity` is passed again. Found in the dashboard's co-spend test.
4. No helper for the miner's text in a coinbase script. `inspectTransaction` returns the script and the BIP 34 height; the dashboard pulls printable runs out of the rest itself (`coinbaseTag` in `src/facts.ts`). A `coinbaseText(script)` that skips the height and extra-nonce pushes would be more exact.
5. V4 certificates carry a device class. A testnet explorer (explorer.pearlified.com, read 2026-11-18) shows a `device` value per V4 block, which it names Blackwell or Hopper. When pearljs parses V4 it should expose that field; read its position from the `fp8-scheme` branch's wire code, not from the explorer.
6. The chain follower asks for `getbestblock`, a btcd method that pearlchain.live's public endpoint refuses, though pearljs's "Choosing a backend" guide points to that endpoint. `src/node.ts` answers it from `getblockchaininfo`, which has the same height and hash. The follower could ask for `getblockchaininfo` itself, or fall back to it.
7. No client-side rate limit. The same guide sets up the public endpoint with `retry` and `maxConcurrentRequests: 1`, which is enough for a wallet, but an indexer reading a block after another runs through the endpoint's token bucket and then gets a 429 on most calls. `src/pace.ts` wraps `fetch` in a bucket priced like the endpoint's table. A `rateLimit` option on `PearldClient`, with per-method costs, would do it in one place.
8. The public endpoint's websocket feed (`wss://pearlchain.live/rpc/ws`) sends its own `{"type":"block"}` messages, not pearld's notifications, so `PearlWsClient` cannot use it and `followChain` polls. An adapter that turns those messages into the follower's wake-ups would make new blocks show up at once.
